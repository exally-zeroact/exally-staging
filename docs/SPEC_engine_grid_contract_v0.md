## 2. 呼び出しの型（何を渡して、何が返るか）

### 2.1 レジストリ（新設・1ファイル）

```js
// lib/op-registry.js
OpRegistry.register(op)      // op.id で登録。同じidの二重登録は投げる（黙って上書きしない）
OpRegistry.get('payroll.monthly')   // → op（無ければ null）
OpRegistry.list()            // → [{id,title,desc,version}]  ★チャットのカタログ／グリッドの関数一覧に使う
```

### 2.2 呼び出しの型（1つだけ。グリッドもチャットも同じ）

```js
const result = OpRegistry.get(id).engine(inputs)
```

**入力 `inputs`** … `op.inputs` の spec に従う素のオブジェクト。**セルでも自然文でもない**。
面（グリッド／チャット）が「自分の形 → inputs」に直してから渡す。★変換は面の責任。

**返り `result`** … 常にこの5つ。**成功でも失敗でも同じ形**（呼ぶ側が分岐を書き分けなくていい）。

| キー | 中身 | 決まり |
|---|---|---|
| `value` | 業務の答え（人ごとの明細と合計など） | ★検証NGなら **null**。0円や空を「成功」として返さない |
| `cells` | 表に置く形（AOA） | Excel出力と**同じ物**を使う＝画面とファイルがズレようがない |
| `warnings` | `[{code, level, scope, text, …}]` | 止めない。黄色い注意 |
| `errors` | `[{path, code, message}]` | `path` は `employees[3].fuyou` の形＝**どこが悪いか客に言える** |
| `provenance` | どのオペ・どの版・**どの年度の法定値が実際に選ばれたか** | ★「なぜその金額か」を後から言えるため |

### 2.3 面ごとの呼び方（両方とも同じレジストリ・同じengine）

```
グリッド  =PAYROLL.MONTHLY(会社設定, 従業員範囲, "2026-07")
            → book.html の関数が inputs に直す → engine → result.cells をセルへ展開
チャット  「7月の給料を出して」
            → /api/claude が【意図をオペidに解決】＋足りない入力を聞き返す
            → 同じ engine → result を見せる
            ★文字の数式を返さない。検証済みオペを呼ぶ。ここが穴の根治。
```

## 3. 責任の線（ここが契約の本体）

```
┌─ エンジン側（オペレーション） ─────────────────────────┐
│ ★業務の答えを出す唯一の場所                              │
│  ・金額・税・保険料・警告・法令の年度切替                 │
│  ・入力の検証（境界で弾く）                               │
│  ・result の5つを返す                                     │
│  ・headless（DOM・通信・乱数・現在時刻に触らない）        │
│  ★やらない: 画面に出す／ファイルを書く／セルを読む        │
└──────────────────────────────────────────────────────────┘
┌─ 面（グリッド／チャット）─────────────────────────────┐
│ ・自分の形 → inputs への変換                              │
│ ・result の見せ方（セルへ展開／文章にする／色を付ける）   │
│ ・ファイルの保存（XLSX.writeFile を呼ぶのは面）           │
│ ★やらない: 金額の計算。1円たりとも面で計算しない          │
└──────────────────────────────────────────────────────────┘
```

**境目の判定に迷ったら1つの問いで決める：**
> **その処理を消したら、答えの金額が変わるか？**
> 変わる → エンジン側。変わらない（見え方だけ変わる）→ 面。

## 4. `payroll.monthly` を、この型でどう呼ぶか（具体例1本）

**現物の記述子（`kyuyo/ops/payroll.monthly.js` から）**

```js
id: 'payroll.monthly'  version: '1.0.0'
title: '月次給与計算'
desc:  '1社1ヶ月の給与を全従業員ぶん計算し、明細・集計・Excel・法令の黄警告を返す'
inputs: { ym, company, employees[], … }   // 型・必須・enum を spec で持つ
law:    { basis, nendo, version }
excel:  { export(result) }                 // 純関数。writeFile は呼ばない
tests:  ['ops-payroll-monthly', 'ops-golden-parity', 'law-switchpoints', 'op-contract']
```

**グリッドから（新設する関数1つ）**

```
A1: =PAYROLL.MONTHLY(設定!A1:B20, 従業員!A1:Z50, "2026-07")
```

| 段 | 誰が | 何をする |
|---|---|---|
| ① | book.html の関数 | 範囲を読み、`{ym, company, employees[]}` に**詰め替えるだけ** |
| ② | `OpRegistry.get('payroll.monthly').engine(inputs)` | 計算。★ここだけが金額を決める |
| ③ | book.html | `result.errors` があれば **その場に赤で出す**（`path` からセルを特定）。無ければ `result.cells` を展開 |
| ④ | book.html | `result.warnings` はトーストで出す（止めない） |

**チャットから**

```
客: 「7月の給料を出して」
→ /api/claude: 意図 → id='payroll.monthly' に解決。inputs の required で足りない物を聞き返す
→ 同じ engine を呼ぶ
→ 「7月分、8人ぶん出しました。うち1人が最低賃金を下回っています（山田さん）」＋表
```

★**チャットが数式を書いて答えにしない。** オペを呼んだ結果だけを見せる。

## 5. ★「業務ロジックを数式で再実装しない」を機械で守る（型として）

**言うだけでは守られない。** 守りの型（今6つ）と同じやり方で、CIで止める。

### 守り方1：オペの外に金額の計算を書かせない
```
tests/op-boundary.test.mjs（新設）
 ・ops/*.js が lib 以外の計算を持っていないか（四則演算のべた書き・税率の直書きを検出）
 ・★面（book.html / chat.html）に、法定の数値（料率・控除額・最賃）が直書きされていないか
   → 見つけたら赤。「その数字は lib にある物を呼べ」と出す
```

### 守り方2：オペは tests が緑でないと公開できない
```
 ・op.tests に書いたテストが CI で回っているか（ci-coverage と同じ照合）
 ・回っていないテスト名が書いてあったら赤（嘘のゲートを許さない）
```

### 守り方3：同じ計算が2箇所に生えない
```
 ・既にある no-duplicate-libs（法定データは例外なし）をそのまま使う
 ・★オペが呼ぶ lib は kyuyo/lib/ の1本だけ、を型として足す
```

### 守り方4：`provenance` を必ず返す
```
 ・engine の返りに provenance が無ければ赤
 ・★「なぜその金額か」を後から言えない計算を、契約が受け付けない
```

## 12. ★法定データの出典・確認日・指紋は「中央 statutory 表」が唯一の正（2026-08-03 決定）

> **人が直すのは中央 statutory だけ。lib 側の写し（`kyuyo/lib/statutory-central.generated.js` と `saitei-chingin.js` の47県）は `scripts/pull-statutory.mjs` が機械で作り直す。★lib を手で直さない。★**

理由：出典・確認日を lib にも手書きすると、中央と lib の**2箇所に手書きが残り、どちらを触っても片方が腐る**（＝確認日が静かに嘘になる）。
ズレていないことは `scripts/pull-statutory.mjs --check`（CI・中央と突き合わせ）と
`kyuyo/tests/statutory-freshness.test.mjs`（CI・ネット不要／指紋で突き合わせ）の2本で見張る。
lib が持つ「人の覚え書き（何をどこまで確かめたか）」だけは `statutory-meta.js` の `NOTES` に残す ―― **値でも日付でもないので中央と競合しない**。

### 12.1 発効日の書き方（★次に中央を読む人へ）

> **中央 statutory は発効日を【和暦】で持つ（例 `令和8年3月31日`）。一次情報の表記を落とさないため。
> 使う側が ISO（`2026-03-31`）へ直す。★自前の変換を書かない。★ `SAITEI_CHINGIN.toIsoHatsuko` / `toWarekiHatsuko` の1箇所だけを使う。**

理由：日付の判定（発効前か後か）は文字列比較でやるので ISO でないと壊れる。
変換が2箇所以上に生えると、そこからドリフトが生まれる（和暦の元号加算をどこかで間違える）。
両方向は `kyuyo/tests/integration.mjs`（中央の形で hydrate して ISO で入ることを実測）で固定してある。
