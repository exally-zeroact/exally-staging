# ROADMAP — Exally 実装セッション用（exally / スイート基盤）

参照必須: `docs/business/00_MASTER_DESIGN_2026-07-25.md` ＋ メモリ（project_exally_suite_redesign_2026-07-25 / project_exally_gyaku_excel / project_exally_rebuild_embed_apps / reference_payslip_supabase_setup / feedback_* HARDルール）。
このロードマップは「Exally（スイートの器・共有基盤・台帳・きく）で何を・どの順で・どこまでで完了か」を定義。経営セッションが更新。実装はこのセッションが担当。

## 分担
- **Exallyセッションが持つ**：スイートの**共通基盤3つ**（①共有課金/利用権 ②共有データ ③「きく」共通エンジン）＋ハブ＋**日次/期間台帳**＋**事業横断の集計**。
- **提供する（Kyually等が消費）**：共有データスキーマ・利用権/決済・「きく」エンジン。→ **スキーマ/契約を先に確定**し、Kyuallyセッションが並行して配線できるようにする。
- **触らない**：Kyuallyの給与計算ロジック（Kyuallyセッション側）。

## 現状
- 本番Exallyは stale MVP（自作スプレッドシート＋AIチャット＋帳票テンプレ）。**「Excelの代わり」の看板は撤去**し、**スイートの器**へ作り直す。逆Excル（対話→チップ→表）が中核。

## 大前提（看板・方針）
- **汎用Excel代替として売らない/作らない**（負ける＝確定）。Exally＝**「繋がって・言うだけで・集計まで見える」グレー中小の事務の土台**。
- 全UIは軽いミント基調（実ブランド **#F0FAF4 / #52B788 / #3D9E72**・ロゴDM Mono・本文Noto Sans JP）＝Kyuallyと統一。

## 共通ルール（各マイルストーン厳守）
完全設計→**テスト先行**→一気実装→**対立監査**→**実UI確認**→**見せてOK後push**。dependency方針はExally既存に合わせる。**捏造禁止**（きくのチップは実データ接地・不明は要入力）。「きく」は入口/補助で唯一の入力にしない。AI従量は**共有キー＋rate-limit＋共通課金**で回収。

## E0【最初に確定・Kyuallyの並行作業を解錠】共有データスキーマの契約
- **目的**：Kyuallyセッションが待たずに配線できるよう、**共有マスタのスキーマ**を先に確定（実装は最小でよいが"形"を固定）。
- **スコープ**：Supabase 共有マスタの定義（`reference_payslip_supabase_setup` の pay_* / 倉庫共有 に準拠）：
  - **従業員マスタ**（KyuallyのdefEmp形と互換）／**取引先**／**自社情報**（屋号/住所/インボイス番号/印影）／**日次-期間台帳**（人×日付×{売上/時間/金額}）。
  - **利用権**（exally_entitlements＝稼働中）を1アカウント横断で使う定義。
- **受け入れ条件**：スキーマ仕様書を `docs/business/SPEC_shared_schema.md` に出す（両セッションの契約）。

## E1 スイートの器（1アカウント・ハブ・共有データ・集計の骨）
- **目的**：1ログインで契約したモジュールが開くハブ＋共有データの読み書き＋横断集計の土台。
- **スコープ**：ハブ画面（タイル：給与/台帳/請求見積…）／共有データの読み書き（E0スキーマ）／entitlementsで解錠／最小の横断集計ビュー（事業別）。
- **受け入れ条件**：1アカウントでハブ→各モジュール、共有マスタが全モジュールから読める、事業別に集計が出る。
- **テスト**：データ層の実データテスト＋UI（ログイン→ハブ→モジュール遷移・例外0）。

## E2 日次/期間の柔軟な台帳（逆Excル）
- **目的**：各社バラバラの溜め方（司さんの代行=売上×0.35＋保障・日々INDEX/MATCH集計 等）を、**対話→チップ→表**で管理。**Kyuallyの二度手間を消す源**。
- **スコープ**：人×日付で {売上/時間/金額} を毎日/できる時に入力→**締め方（日次/週次/N日/1-10・11-20・21-末）で自動集計**→期間結果を出す（Kyuallyへ渡せる形）。決め方（率・保障・日額）を"きく"で設定。
  - **境界**：構造化台帳＋ルール（率/保障/日額）まで。**独自マクロ（売上1/2/3・距離）そのものは再現しない**＝率で表せる範囲 or 日額入力。代行は将来 **Daikome→台帳** で自動供給。
- **受け入れ条件**：日々入力→10日締めで期間の支給額が出る→Kyuallyに渡せる。捏造なし（不明は要入力）。
- **テスト**：集計ロジックの実データ＋UI（日次入力→期間集計→受け渡し）。

## E3 「きく」共通エンジン（最小版・署名/堀）
- **目的**：**対話→チップ→正しい成果物**を全アプリ共通の部品に（アマかせ「きく」を移植）。
- **スコープ**：`/api/scan` 相当（Claude・共有キー ANTHROPIC_API_KEY・サーバ側）＋対話状態＋**実データ接地のチップ生成**＋構造化出力（各モジュールのスキーマへ）。rate-limit（ask_usage型）。**キー無し/失敗時はルールで動く**フォールバック。
- **受け入れ条件**：台帳/帳票で「言う→逆に聞かれる→チップで選ぶ→表/成果物」が動く。捏造なし。コスト上限が効く。
- **テスト**：純関数（マッピング/フォールバック）＋UI（対話→チップ→成果物）。
- **司さん手番**：ANTHROPIC_API_KEY（Exally流用・新規課金なし）をVercel envに設定（実装セッションは生キー非タッチ）。

## E4 共通決済（Stripe）
- **目的**：スイート/各SKUの本番課金を**共通決済1つ**で（アプリ別に作らない・アマかせの器は共通へ統合）。
- **スコープ**：Checkout＋Webhook署名検証＋entitlements連携（1 Stripe・1基盤）。SKU＝Exallyスイート/Daikome/アマかせ。
- **前提/優先度**：**当面はKyuallyの手動請求＋entitlementで足りる**＝E4は有料客が増えて手作業が辛くなってから。**司さん手番**：Stripe本番接続（実支出・生キー非タッチ）。
- **受け入れ条件**：1つの決済基盤で複数SKUの解錠。

## E5 集計・事業横断ビュー（両モジュールから見える）
- **目的**：司さんの多事業（代行/空調/EC）を**1つの集計**で。スイートの価値の見える化。
- **受け入れ条件**：事業/職種でグループ化した集計を Exally からも（将来Kyuallyからも）見れる。

## 差別化モジュール（E1〜E3の後・1つずつ）
請求＋見積（見積→請求ワンタップ）→ 外注/業務委託＋支払調書 → 現場見積＋作業報告書（空調・逆Excル）→ 案件原価・粗利 → 入金/未回収 → 現金出納。すべてグレー/現場/どんぶり軸。**一気に作らない。**

## 順番
E0（スキーマ契約＝Kyually解錠）→ E1（器）→ E2（台帳）→ E3（きく）→ E5（集計）→（有料増）E4（共通決済）→ 差別化モジュール。
